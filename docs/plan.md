# serenedb-log-mcp implementation plan (Phase 2)

> **For agentic workers:** this is a project plan made of tickets, not a step-by-step code plan. Each ticket becomes a GitHub issue labelled `ticket`. The implementer of a ticket works test-first with `superpowers:test-driven-development`, follows `overnight/PROMPT.md` section 6, and reads the Decision proposals linked in the ticket before writing code.

**Goal:** a read-only MCP server over SereneDB that lets Claude answer Engineer, Team Lead and Manager questions about the Base Corpus with cited Evidence, then extends to the award tracks (agent-managed index with benchmark, huge datasets, multimodal correlation, access control per Role).

**Architecture:** a post-load derive step turns the loader's raw tables into canonical tables, a Pattern dictionary and a default Incident table inside SereneDB. Parameterised tools run fixed SQL templates through one read-only database layer, wrap every result in an Evidence envelope, record it in the Evidence Ledger and shape it per Role. Claude checks its draft with `verify_answer`, and `export_investigation` turns a session into the worked investigation.

**Tech stack (settled):** Python, the official MCP SDK (`mcp` 2.3.0, where FastMCP is now `mcp.server.mcpserver.MCPServer`), psycopg 3, `uv`, pytest, ruff, mypy. SereneDB 26.10.1 on the Postgres wire protocol, port 7890.

Status: drafted overnight by NoNaim95's Claude (leader) on 2026-10-16/17 from the Decision proposals on issues #1 to #7. All seven research issues have `consensus`: #1, #2, #4 and #5 by both Claudes, and #3, #6 and #7 by the leader alone while OrFrederick's Claude was absent. Nothing here is confirmed by the humans yet. Assumptions are listed in [Open points and assumptions](#6-open-points-and-assumptions).

**Limits** (#2 Decision proposal): `search_logs` rows default 20, maximum 50; `count_by` groups default 25, maximum 100; `get_context` default 10, maximum 50 entries per side; `trend` at most 400 buckets; `list_incidents` default 20, maximum 100; `top_patterns` default 20, maximum 50; `latency_stats` maximum 50 groups. Messages are capped at 240 characters per row. Responses stay under Claude Code's 10k-token warning and 50k-character spill threshold.

**Evidence envelope** (T3, every Evidence tool): `evidence_id`, `tool`, `role`, `sql[]`, `params[]`, `data_scope{datasets, time_from, time_to, time_input, resolved_against, filters}`, `total_matches`, `returned`, `truncated`, `query_ms`, `columns[]`, `rows[][]`, `summary{}` (tool-specific scalars such as `share_pct`, `top_n_sum`, `other_count`, `groups_total`, `entries_total`, `incidents_total`), `notes[]` (steering text, hints, truncation notes), `answer_frame[]` and `not_measured[]` (Role layer). The text content mirrors the same JSON for clients other than Claude Code. Errors are raised as `ToolError` with an actionable message, because on errors only `content[0].text` reaches the model and in `mcp` 2.x only `ToolError` text survives.

**Prompts:** `engineer`, `team_lead`, `manager`, each with single-token arguments because Claude Code splits prompt arguments on whitespace (T7).

**Server instructions** (at most 4,096 characters, T7): the Datasets; retrieval returns samples and aggregation answers frequency; cite `[E<n>]` next to every number and quote exact numbers; Log Entries are not Incidents; answer in four sections (Observed Facts, Hypotheses, Unknowns, Next Step); call `verify_answer` before answering; the Role prompts and `get_role_brief` exist.

**Resources:** none planned. The #2 research proposed depth-only resources; every fact they would carry is already reachable through a tool, and Claude Code does not read resources automatically.

### 2.4 Database access layer (T2)

- **Read-only:** every statement runs in a read-only transaction (psycopg `conn.read_only = True`, which issues `BEGIN READ ONLY`). `SET default_transaction_read_only` is not enforced by SereneDB, so it is not used.
- **Timeouts:** `statement_timeout` is accepted but not enforced. A `threading.Timer` calls `conn.cancel_safe()` after `SLM_QUERY_TIMEOUT_S` (default 15 s); the connection stays usable afterwards (measured in #2).
- **Retry and reconnect (#2 round 2):** SereneDB 26.10.1 crashes with SIGSEGV intermittently, the crash can hit an innocent later call, and binding mode makes no difference. On a lost connection (`OperationalError`) the layer waits until `select 1` succeeds on a new connection (a restart took about 2 to 3 s), retries the statement once and adds a note to the envelope. If the retry fails too, it raises a `ToolError` that says the database restarted and suggests `sort=time`.
- **Binding:** parameters are always bound, never formatted into SQL. psycopg's default server-side binding is used; `SLM_CLIENT_BINDING=1` switches to `psycopg.ClientCursor`. Injection strings were inert in both modes (#2).
- **Relevance sort (#2 round 2):** `sort=relevance` uses `ORDER BY BM25(idx.tableoid) DESC LIMIT n` with no tie-break key after the score. A tie-break key after the score crashed native 26.10.1 in 28 of 70 runs; the single-key form crashed in 0 of 44. `sort=time` is the default. Because ties are unordered, replays compare `total_matches` for relevance results, not row identity.
- **Limits and truncation:** the exact total comes from a separate `count(*)` (faster than `count(*) OVER ()`); the row query is skipped when the total is 0; `truncated = returned < total_matches`.
- **SQL rules:** fixed templates only; identifiers come from enums and the Dataset registry, never from input; user text goes through `websearch_to_tsquery`; in relevance mode, filters use `col @@ ts_between(...)::score(NULL)` so they do not change BM25 scores; point lookups (`get_context`) run on the base table, never through the inverted index. On 26.09.1.3 with an index over a view, a `line_no` predicate made the index ignore the `ts` filter; it did not reproduce on 26.10.1 with a base-table index, but base-table lookups are cheap and correct either way (#2).
- **Per-Role connections:** `DATABASE_URL_<ROLE>` when set (T22), otherwise `DATABASE_URL`.

### 2.6 Environment facts the implementation relies on

- SereneDB 26.10.1 (dev) speaks the Postgres wire protocol on port 7890. The dev instance runs on a remote box behind an SSH tunnel and is shared by all implementers. The documented route for judges is a local `docker run serenedb/serenedb` with `-e SERENEDB_HOST_AUTH_METHOD=trust`.
- `statement_timeout` and `default_transaction_read_only` are not enforced; use `cancel_safe()` and `BEGIN READ ONLY`.
- The server SIGSEGVs intermittently. The known trigger is a BM25 sort with a tie-break key after the score (28 of 70 runs on native x86_64 26.10.1); parameter binding is not a factor, and a crash can surface on a later query. The database layer must reconnect and retry, and no SQL template may sort by BM25 plus a second key.
- `CREATE TEXT SEARCH DICTIONARY … AS split_text(...)` exists only from 26.10.1. OrFrederick's Claude verified the legacy `(TEMPLATE='segmentation')` form on 26.09.1.3. The derive step picks the form by server version.
- `time_bucket` drops empty buckets; gap-fill with `generate_series(timestamp, timestamp, interval)`.
- A bare `@@ 'a b'` is OR; `websearch_to_tsquery` gives AND and quoted phrases.
- The inverted index is eventually consistent; run `VACUUM (REFRESH_TABLE) <table>` after loading and after `CREATE INDEX`.
- A SELECT-only login role can still read server files (`read_csv('/etc/passwd')`) and change some server-wide settings, such as `enable_external_access`. Never run experiments that `SET` server-wide settings on the shared instance.
- `mcp` 2.3.0: `from mcp.server.mcpserver import MCPServer`, `from mcp.server.mcpserver.exceptions import ToolError` (as used in `research/2-NoNaim95:research/2/NoNaim95/prototype/server.py`).
- Claude Code 2.1.293 shows the model only `structuredContent` on success and only `content[0].text` on errors. Without `_meta["anthropic/alwaysLoad"]` the tools sit behind ToolSearch. `outputSchema` is never shown to the model, so each description must summarise its output fields.
- The dev loader (`/Users/deni/hackathon/tools/dev_loader.py`, moved into the repo in T1) loads `bgl(line_no, alert_tag, epoch, ts, node, component, level, message, raw)`, `openstack(line_no, source_file, log_file, ts, pid, level, component, request_id, instance_id, message, raw)`, `lh2_bgl` and `lh2_openstack`. It is throwaway and is not the organisers' loader. The organisers' loader, schema and Ownership Table have not arrived.

### T2: Database access layer and Data Scope
- **Owner:** N. **Area:** data access. **Blocked by:** T1. **Links:** #2 Decision proposal and NoNaim95's Research (safety table), plan section 2.4.
- **Goal:** one module through which every tool runs SQL, so that read-only enforcement, timeouts, crash recovery, truncation and Data Scope handling are written once and tested once.
- **Acceptance criteria:**
  - [ ] Every statement runs in a read-only transaction. A `db` test shows that INSERT and CREATE through the layer fail, while a full-text query, a `GROUP BY` and a `time_bucket` query succeed.
  - [ ] A `threading.Timer` calls `conn.cancel_safe()` after `SLM_QUERY_TIMEOUT_S`. A `db` test with a deliberately slow query and a 0.5 s timeout raises the layer's timeout error within about 2 s, and the next query succeeds.
  - [ ] On a lost connection the layer waits until `select 1` succeeds on a new connection (bounded wait), retries the statement once and adds a note to the envelope; if the retry fails, it raises a `ToolError` that says the database restarted and suggests `sort=time`. Unit-tested with a fake connection that fails once and one that always fails.
  - [ ] `fetch_limited(count_sql, rows_sql, params, limit)` returns `total`, `rows` and `truncated`, and skips the row query when the total is 0. Parameters are always bound (psycopg's default); `SLM_CLIENT_BINDING=1` switches to `psycopg.ClientCursor`, and an injection string passed as a value matches 0 rows in both modes.
  - [ ] `scope.py` validates enum inputs with "did you mean" hints (`KERNAL` suggests `KERNEL`), and resolves relative times such as `last 7d` against the Dataset's last timestamp. The Data Scope records both the input and the resolved range.
  - [ ] Table and index names are qualified with `SLM_SCHEMA`, which is validated against `^[a-z_][a-z0-9_]*$`.
- **Reuse:** `_q` in `research/2-NoNaim95:…/prototype/server.py`; `research/2-NoNaim95:…/survey/exp_readonly_tx.py`; `research/2-OrFrederick:…/deliberation/throwaway_db/c4_readonly.py` and `c5_timeout.py`.

## 6. Open points and assumptions

### Assumptions made overnight (each needs human confirmation)
1. **Tool set (#2):** the plan adopts OrFrederick's Decision proposal (12 tools plus 2 stretch tools) with NoNaim95's round-2 amendments, and adds the tools that later Decision proposals call for: `get_role_brief` (#4), `list_patterns` and `search_patterns` (#7), `list_incidents(similar_to=…)` (#7, a parameter rather than a tool), `get_trace` as the multimodal stretch tool, and `find_patterns` as the OTel stretch tool (#7). That makes 15 core tools. Evidence: #4 and #7 recommend these tools and the #2 proposal predates them.
2. **Binding and crashes (#2 round 2, consensus):** psycopg's default binding, `ClientCursor` behind a switch (default off), no BM25 sort with a tie-break key, and reconnect plus one retry with a note. Evidence: 182 executions on native 26.10.1, where the two-key BM25 sort crashed 28 of 70 times regardless of binding mode and the single-key sort 0 of 44.
3. **Overlap among `list_patterns`, `search_patterns` and `top_patterns`:** kept as three tools with explicit "use X instead" lines, as the #7 Decision proposal says, because their outputs differ (a catalogue, a lexical search, a ranking with Incidents). The L1 eval (T17) measures confusion. If it is high, fold `search_patterns` into a `query` parameter of `list_patterns`.
4. **Role argument scope (#4):** `role` is required on every Evidence tool, on `verify_answer` and on `get_role_brief`. `get_evidence` and `export_investigation` are Role-agnostic, because they return or render stored Evidence.
5. **Manager and raw lines (#4):** for the Manager, `search_logs` and `get_context` withhold rows and keep totals and facets, instead of raising an error. Evidence: #4 says a Manager answer "cannot cite raw lines it never got".
6. **`export_investigation` writes a local file**, so it is not marked read-only. It never writes to SereneDB.
7. **Template mining (#6, leader alone):** the plan follows the Decision proposal (Tier 1 SQL `CASE` chain from Loghub-2.0 with strict wildcards first and a scoring gate, Tier 2 generic g10 masks, a dictionary per distinct message). One open question is answered by assumption: the Tier 1 SQL is generated at derive time from the Loghub-2.0 files that `scripts/fetch_data.py` downloads, and neither the template files nor the generated SQL are committed, with a switch to turn Tier 1 off. So the licence question does not block work, and a "no" from the humans costs one environment variable.
8. **Canonical term:** "Pattern" is the concept and `template_id` the column (#6 Decision proposal); "template text" is the text of a Pattern; "Pattern Family" names the drift merge (`family_id`). Proposed in `GLOSSARY.md` under "Proposed terms".
9. **Embeddings (#7, leader alone):** the catalogue path (`list_patterns`, with `search_patterns` as the fallback) is the core. The optional vector `find_patterns` for the OTel track is the stretch ticket T26, with `fastembed` for query embeddings (no key), after the core and the index-benchmark track.
10. **Time zones:** `trend` buckets and displayed times use `ts` as logged (US Pacific local time for BGL), and the Data Scope says so; all gap arithmetic uses `epoch_utc` (#1).
11. **Parameters (#1):** `gap_s` and `merge_scope` stay tool parameters with the documented stable band; the Manager ranking weights stay fixed and equal (#4 recommendation).
12. **Access control (#4):** presented as defence in depth with the limits stated in the README.
13. **Tool names:** no prefix; the server name `serenedb-log` already namespaces them in Claude Code.
14. **Shared dev instance:** implementers isolate derived tables with `SLM_SCHEMA`, and never run experiments that change server-wide settings.
15. **CI data:** CI uses the Loghub 2k samples, downloaded at run time; golden numbers are checked locally against the full Base Corpus (`corpus` marker), because loading 4.7M lines in CI is slow.
