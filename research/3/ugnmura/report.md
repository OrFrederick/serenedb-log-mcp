# Tool-selection and answer-quality evaluation — independent research

Researcher: **ugnmura's Codex**, 2026-10-17. No other Research comments read. This document is a recommendation, not a confirmed project decision.

## Recommendation and confidence

Use **pytest + the official MCP Python SDK for deterministic protocol/data contracts**, then **promptfoo's native Claude Agent SDK provider for live Claude trajectory and answer evaluation**. Store the same versioned cases and independent golden SQL in the repo; join the model trace to the actual per-run Evidence Ledger. Keep human calibration for Role quality and unsupported causal/impact claims. Use Inspector as a manual/CLI interoperability probe, not as a substitute for an agent eval. This evaluates the intended Claude-with-MCP product without creating a custom product agent.

Confidence is **high** in the contract and assertion design, **medium** in choosing promptfoo over a small direct SDK runner: current primary documentation explicitly supports local MCP and tool-call metadata, but a live Claude run has not been executed here. The protocol prototypes ran with official **mcp==2.3.0**. No Claude CLI or model API was invoked; no keys were present in the environment. There is no measured Claude pass rate yet.

## Experiments and their precise limits

Run from this worktree:

```sh
uv run --with mcp==2.3.0 python research/3/ugnmura/experiment.py
uv run --with mcp==2.3.0 python research/3/ugnmura/stdio_experiment.py
```

`results.json` records real in-process server/client calls in auto, legacy and 2026-07-28 modes. All discover one tool and three Role prompts, retrieve a prompt, return six matching fixture entries with one of three groups displayed and `truncated=true`, and reject missing Component / limit 51 before executing the tool body. `stdio-results.json` additionally passes discovery, prompts/get and tools/call through actual subprocess/stdio in both legacy and 2026-07-28 eras (timings retained per run in the JSON; single runs are not a performance benchmark).

SDK migration findings verified against installed 2.3.0 and these executions: `MCPServer` replaces v1 `FastMCP`; `Client(server)` replaces the removed in-memory helper; use mode `2026-07-28` rather than literal `modern`. Python model fields are snake_case (`input_schema`, `structured_content`, `is_error`), while wire aliases remain camelCase. A generic dictionary return needed explicit `structured_output=True` and an appropriate return annotation to produce the output schema we asserted. Product tools should use concrete Pydantic Evidence models rather than generic dictionaries.

The fixture comes from a real independent offline scan of the raw OpenStack archive, SHA256 `87c98c5ed03262e05cdb7a6f3717033df76d88fda0f7d2db23bd9fa4200f1879`; it is deliberately labelled `source_kind=offline_fixture`, `query_sql=null`. **It is not SereneDB Evidence and not a SQL golden.** SQL assertion execution belongs to the final database-backed integration suite after loader/schema confirmation. The prototype does not claim MCP protocol itself adds missing ledger semantics.

One positive typed-claim answer passes. Seven deliberately wrong answers are rejected: wrong value, dangling typed citation, same numeral but wrong metric, wrong Data Scope, missing Unknowns, invented financial loss, dangling prose citation. The positive answer says cost/downtime are unknown, showing why keyword banning would be wrong. The experiment deliberately exposes a residual defect: a false extra prose claim, “9 incidents”, passes a checker that only checks typed claims. Therefore **typed claims alone do not prove every prose number**. Make measured tables render from validated claim objects, and independently extract/review all free-text measured claims before publishing the worked investigation. Do not call mutation-test pass rates Claude accuracy.

## Assertion contract

Persist `case_id`, repeat, Role, exact prompt text/hash, tool descriptions/schema hash, model/version, SDK versions, corpus/loader/index/Ownership Table hashes, run/session id, request ids, structured results, errors, token usage, model cost, query and total latency, answer, scores, and grader version. New ledger namespace per trial: E1 from another run must never resolve accidentally. Capture authoritative tool output before any redaction/postprocessing and compare with the model-visible result; do not trust self-reported calls.

1. **Calls**: each case defines needed capabilities and acceptable alternatives, forbidden calls, and argument predicates. Engineer context requires a real entry returned by search and the same correlation scope. Aggregation may precede or follow search. Assert a partial order only when one call consumes another's output; exact full paths reject valid strategies. Parallel calls are a graph, not a reliable total order.
2. **Arguments**: exact Dataset, `[start,end)` boundaries/timezone, severity set, query mode/phrase, limit bounds, grouping dimensions, Component/Team mapping policy and comparison denominators. Reject silent filter changes. Retry behavior and timeout classification are separate checks.
3. **Data correctness**: independent, reviewed SereneDB golden SQL computes expected metrics against the same loaded corpus. Store executed SQL, typed parameters, results and source version. Counts compare exactly; decimals compare with declared scale/tolerance; rates carry numerator, denominator, units and interval. Never reuse production query-builder output as an independent oracle. Samples never establish prevalence.
4. **Claim grounding**: typed claim `{metric, value, unit, scope, evidence_id, result_path}` must resolve to successful Evidence in this run, the right metric and scope, then independent golden. Verify rounded display values against declared precision. Dates, status codes, UUIDs, version numbers and entry ids are not all prevalence claims; regex on numerals alone is insufficient. Evidence ids cannot merely exist: they must support the adjacent assertion.
5. **Role substance**: Engineer has specific lines/context and a discriminating check; Team Lead has recurrence/coverage/Ownership Table and an investigation order; Manager has measured priority, uncertainty and a decision. Same Evidence is allowed when relevant, but swapping Role labels on identical sections/actions fails.
6. **Answer sections**: Observed Facts, Hypotheses, Unknowns, Next Step must be nonempty or explicitly “none established”. Separate observation from cause; Log Entries from incidents. Manager invented financial loss/downtime/customer impact fails; stating that they are unknown passes. Log text and tool output are untrusted data, not instructions.
7. **Error / absence**: timeout is not zero, unavailable Ownership Table is not a guessed Team, truncation is not completeness, zero baseline is not a finite percentage change. Entire suite must use retrieval + aggregation, both Base Corpus Datasets, one full-text search and a whole-Base-Corpus aggregate; not every Role needs every capability on every question.

Output JSON schema enforcement is available in the live SDK harness; it does not automatically constrain free-form Desktop/Code final answers. In the product, MCP `outputSchema` validates tool outputs, not the host's final response. Evaluate the same Markdown workflow users see as a separate compatibility lane. Retrieve the actual MCP Role prompt via `prompts/get` during setup and inject that exact text; connecting the SDK to MCP does not establish that a Role prompt was selected.

## Questions, repetition, judging and statistics

`questions.json` has **10 questions per Role + 12 adversarial cases** (42 cases). It includes shared token-validation questions for cross-Role contrast, Base Corpus totals, phrase/fuzzy/time/context selection, zero matches, truncation, ownership gaps, noisy-node concentration, incomparable files, unsupported cost/downtime, fake Evidence ids, prompt injection and timeout. Add the labelled INFO-level slow-build story from issue #1 as a further held-out triplet so severity-only search cannot pass. Freeze hidden expected SQL/results outside the evaluated agent's tools; no shell/file-reading tools or internet access in live eval.

Proposed cadence, not a statistical law: PR live smoke **one common case per Role + three adversarial, three independent runs = 18 trials**; nightly/release full **42 × 5 = 210 trials**. Pin model and reset session, mutable server state and corpus snapshot each time; disable eval cache. Five trials reveal common instability but are weak evidence per question: 5/5 has a two-sided Wilson 95% lower bound around 57% (computed lower bound 0.5655175 using the [NIST-described Wilson method](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)); report numerator/denominator. Fifteen trials for one Role-question set does not prove every question is reliable. Report trial pass rate and fraction of cases passing all five; do not use best-of-five as reliability. For prompt/description A/B, paired same cases and repeated runs, randomised order, cluster confidence intervals by case; bootstrap cases with all repeats together. Do not treat all 210 trials as independent across question difficulty. Add cases to the bank from failures, retaining a held-out set to limit tuning leakage.

Use deterministic checks for query values, citations, schemas, scopes and required tool capabilities. A calibrated rubric/human check handles causal restraint, action usefulness, Role fit and unsupported semantic claims. Start with about 20 independently human-rated outputs covering all Roles and borderline failures (target to be expanded, not a validated sample minimum), hide model/config identity, double-rate a subset, adjudicate disagreements, and publish judge-human confusion/disagreement. Freeze rubric/model, test position-swapped pairs to detect order bias, rerun calibration after model changes. A judge cannot override a failed numeric/citation gate. [Anthropic's guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) supports combining graders and examining repeated trials; our exact cadence is a project proposal.

## CI, runtime, cost and presentation

PRs/forks: run deterministic MCP + database goldens without model credentials. A fork must never access secrets; do not execute untrusted PR code with `pull_request_target` credentials. Trusted manual/nightly job: start pinned SereneDB, load checksum-pinned corpus/Ownership Table with supplied loader, refresh confirmed indexes, wait for health and test count, run locked Node/Python dependencies, then promptfoo with `--no-cache --repeat 3` for smoke or five for full suite. Attach raw trace, redacted ledger, output and machine-readable score artifact even on failure. Separate infra/auth/rate-limit failures from quality failures while reporting both denominators. Never silently skip an unavailable model and print 100%.

Do a one-case pilot to measure token/cost and p50/p95 wall time. Budget formula is sum over trials of each provider's measured input/cache/output/thinking token cost plus optional judge cost; database/Docker cost reported separately. With mean live cost `c` and seconds `t`, the proposed full suite costs approximately `210*c` and serial runtime `210*t` plus startup. No defensible dollar estimate exists until the actual model and workload are selected. Cap turns, per-trial timeout and SDK budget with headroom (SDK estimate can overshoot); cap total CI duration/concurrency and abort on budget consumption. Do not enable extra tools or permissive mode to avoid proper configuration.

README table proposal: Role | cases | trials | correct-tool-capability | golden numeric/citation | Role rubric | all-gates | all-five consistency | p95 seconds | measured USD. Include corpus/model/date/config hashes, confidence intervals, infrastructure failures and an inspectable failed example. Current truthful row: **Claude quality “not run”; deterministic MCP compatibility “passed”; mutation graders “7 intended failures rejected, known free-text gap”**. This is stronger than an unverifiable 100% claim.
