## BGL: the published failure counts reproduced (T10)

Generated by `uv run python scripts/ground_truth.py bgl` on 2026-10-17 06:17 UTC against schema `rev22_slm` (SereneDB 26.09.1.3).

**Result: 1,202 of 1,202 distinct failures, 9 of 11 published per-category counts exact, 2 false positives and 2 missed at the same threshold.** A false positive here is an Incident we report that the published count for that category does not; a miss is a published failure we do not split out.

**What the labels establish.** Every raw alert count matches exactly, so this is the Dataset the paper studied and our Pattern key is the paper's alert category. The chaining then reproduces the published total exactly and 9 of the 11 published per-category counts.

**What they do not establish.** Three limits, and they matter:

1. `gap_s = 300` was chosen because it reproduces the published total (#1). The total is therefore a fitted number, not an independent one. Only the per-category breakdown is independent, because no constant was tuned on it: the paper publishes one aggregate count and ten per-category counts, and the 300 s was fitted on the aggregate alone.
2. The BGL alert category is both the published label and the Pattern key the derive step chains on, so this check scores the filtering, not alert detection. It says nothing about whether we could find these alerts in an unlabelled log. The OpenStack section of this file is the check that runs without labels.
3. The paper's text states T = 5 s, which gives 1,643 Incidents, +441 against its own published total. That T = 300 s is the intended value is our inference, and the README must say so.

**Threshold sweep.** Only the default gap reproduces the published total.

**This check does not test the time zone.** At 300 s the alert categories chain into 1,202 Incidents on the UTC column and 1,202 on the local `ts`, so the published count cannot tell the two apart. The difference shows only over all 4,747,963 BGL Log Entries, where the same chaining gives 8,149 chains on UTC and 8,148 on `ts`, because the 3,718.57 s gap before 2005-10-30 01:20:02.690798 PST looks like 118.57 s in local time. That single chain is pinned by `tests/corpus/test_canonical_corpus.py`, which is where the time-zone handling is checked.

**The Manager trap.** The largest Incident of the corpus has 152,182 Log Entries on 1 node (R30-M0-N9-C:J16-U01) on 2005-06-11: a Shape of single-node storm. Counting Log Entries makes KERNDTLB the worst problem in the Dataset by a wide margin; counting Incidents shows one node shouting, and the category still holds the published 37 Incidents.

**Shape of the 1,202 Incidents.** 720 single-node isolated, 226 multi-midplane, 136 machine-wide, 119 one midplane, 1 single-node storm.

**Timings.** The Incident derive step took 44.0 s on the full corpus, rebuilt into a temporary table so that this script changes nothing shared; a persistent rebuild measures the same within noise. The number moves with the load on the instance, so compare runs, not absolutes. It builds 48,628 Incidents in total: the 1,202 alert ones scored above, and the rest from the template-keyed Patterns T9 assigns to the non-alert Log Entries, which have no published ground truth.
