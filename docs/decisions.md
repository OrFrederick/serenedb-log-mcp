# Decisions and known facts

This is a living record from the design grilling. **Settled** items are agreed by the team. **Open** items wait for a research issue.

## Settled
- **Name**: `serenedb-log-mcp`.
- **Team**: 3 people. Each person drives their own Claude agents. Time and tokens are not the constraint. The goal is to win, so we do every award track and no half solutions.
- **Stack**: Python with the official MCP SDK, psycopg 3 to SereneDB, `uv` for setup and pytest for tests.
- **Interface**: the MCP server is the product, and Claude (Desktop or Code) is the agent. The Roles are exposed as MCP prompts. There is no custom agent app.
- **Evidence Ledger**: every tool call returns an evidence id, the executed SQL, the parameters, the Data Scope, the total match count, the returned count, a `truncated` flag and the query time. Every call is stored in a ledger. Answers cite `[E<n>]` next to each number. Every answer is split into Observed Facts, Hypotheses, Unknowns and Next Step.
- **Verification**: golden SQL for every worked-investigation claim, enforced by pytest. A replay script re-runs ledger entries and checks the numbers in the final answers.
- **Local dev**: run SereneDB in Docker (`serenedb/serenedb`, port 7890). Point `DATABASE_URL` at either the local instance or the provided instance.
- **Organiser materials**: the official loader, schema and Ownership Table are supplied by the organisers and are the source of truth. We have not received them yet. Until they arrive, a throwaway dev loader unblocks work, and we replace it when the official one lands.
- **Award order**: core requirements first. Best MCP Server is part of the core. Then, in order: agent-managed index with benchmark, huge datasets, multimodal correlation, access control per Role.
- **Multimodal source**: `otel_demo/` in the public-pme bucket, which holds logs, traces and metrics joined on TraceId and stored as remote Parquet. Use Nezha only if we need ground-truth faults.
- **Huge datasets**: query `text_bench/part_000` (1B rows) in place and never index the whole set. The agent builds an index over a time slice on demand. Report rows, wall time and the trade-off between index build time and time saved.
- **Access control per Role**: optional and informal in the brief. SereneDB has no RLS ("Row-level security is not supported"). If we do this track, we use filtered views per Role, a LOGIN role per Role, and GRANT on the views only. The README states the limitation.
- **Log Entries are not incidents**: count entries and derived incidents separately. The incident model is open research, see below.

## Differentiators (settled 2026-10-16)
Most entries will be "an MCP server with search, count and trend tools, plus three answers from Claude". Our edges:
1. **Log Entries are not Incidents, and that is the headline.** Turn line counts into Incidents with Spread or blast radius. BGL node names encode rack, midplane and node card. For example: "152k lines = 3 Incidents: one node looping, one midplane fault, one cluster-wide event". The demo opens with this. Research in #1.
2. **Scored against ground truth.** Report detection results against the BGL alert labels and the OpenStack anomaly instances, such as "found 4/4", in the README and on a slide.
3. **Self-verifying answers.** The agent calls `verify_answer(draft)` before it answers. The tool checks every number and every `[E<n>]` citation against the Evidence Ledger and rejects anything that is unverified or does not match.
4. **The refusal moment.** The Manager asks about cost. The agent refuses to invent a figure, states what the logs measure and what they cannot, and offers the measured alternative.
5. **Visual Evidence inside Claude through MCP Apps** (`io.modelcontextprotocol/ui`, renders in claude.ai and Claude Desktop, not in Claude Code): an incident timeline for the Engineer, a rack heatmap for the Team Lead, a ranked risk table for the Manager. The text `content` fallback is always present. A spike must first confirm that the UI renders over stdio in Claude Desktop. The brief allows a UI ("not required"), and novelty is scored under Execution.
6. **One investigation handed between Roles.** The Engineer, Team Lead and Manager answers chain through shared Evidence ids. We do not give three separate answers.
7. **Baselines on every number**: the previous period, the median week, and a normal or unusual flag.
8. **`export_investigation`** produces the Markdown report of a session. The required worked investigation is generated by this tool, so it can be reproduced.
9. **Demo priority**: line-versus-Incident reveal, then live self-verification, then visuals in Claude, then the ground-truth score, then the refusal. The 1B-row scale result goes on one slide with numbers, not as a live wait.
10. **Optional hosted MCP endpoint** (streamable HTTP, read-only, rate-limited) pointing at the **organiser-provided** SereneDB instance. It is a convenience only. The brief says "use only the tools and resources listed in this brief", so the local stdio path from a clean checkout stays the documented required route.

## Differentiators, round 2 (2026-10-16)
- **Precursor mining (accepted, with a guard).** Across all occurrences of a pattern, find which patterns precede it on the same node within a time window, and compare that rate against the baseline. Report a precursor only when it passes a minimum support and lift threshold that we state. Otherwise answer "no consistent precursor found". No speculative or made-up links.
- **Play to the sponsor (accepted).** Combine search and analytics in one SQL statement (`@@`, BM25, `GROUP BY`, `time_bucket`). Showcase the inverted index over remote Parquet. Show query time in every piece of Evidence. The README gets a "SereneDB features used" section.
- **Pattern-first search (accepted).** The agent searches the template list first and then counts and fetches entries by template id. Vector search is in scope only if it needs no external embedding key.
- **Corpus-relative time (accepted).** Relative times such as "last week" resolve against the corpus end date. The resolved range goes into the Data Scope.
- **Noise versus signal (accepted).** Pareto view in `top_patterns`, with a chronic/benign flag based on level, trend and precursor links.
- **Ownership gaps and cross-team Incidents (parked).** Decide after #4 (Role differentiation) reports.
- **Ticket drafts and decision memo (parked).** Risk of overbuilding. Decide after #4.
- **Hypothesis tracker (dropped).** Out of scope.
- **Judge install (open).** Either a Claude Desktop extension (`.mcpb`) or a self-hosted endpoint. Decide after the spike on MCP Apps over stdio.
- **Demo insurance (accepted).** A recorded backup video and a cached replay of the Evidence.

## Known facts (verified by research agents, 2026-10-16)
- SereneDB speaks the Postgres wire protocol on port 7890, and psycopg 2 and 3 are supported. Example connection: `psycopg.connect("host=localhost port=7890 dbname=postgres user=postgres")`.
- Full-text search uses an inverted index that you query as its own relation: `FROM idx WHERE col @@ ...`. It supports BM25 (`BM25(idx.tableoid)`), `ts_phrase`, proximity `##`, `ts_levenshtein`, `ts_ngram`, `ts_regexp` and `ts_highlight`. The index is eventually consistent, so run `VACUUM (REFRESH_TABLE) t` after loading. Phrase queries need the `position` dictionary option.
- SereneDB has `time_bucket`, `date_trunc`, `epoch` and `make_timestamp(_ms)`, and full window functions. It has **no** `to_timestamp`.
- Remote Parquet: `read_parquet('https://...')` works. Pass a list of URLs, because HTTPS globs are unlikely to work. `EXPLAIN ANALYZE` reports rows and wall time but not bytes scanned. An inverted index over a view of external data is a snapshot, and you refresh it with `REINDEX`.
- `text_bench`: 52 files of about 1B rows each, about 2 TB in total. `otel_demo/`: logs (91.6M rows), traces (216.7M rows) and metrics.
- Loghub-2.0 (Zenodo 8275861) ships full template annotations: BGL has 4,631,261 lines and 320 templates, OpenStack has 207,632 lines and 48 templates. Its Content field holds only the message, and its line counts differ from the raw corpus.
- OpenStack anomalies: reportedly about 4 instance UUIDs with injected faults, visible in timing data but not in message text. Not yet verified.
