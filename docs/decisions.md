# Decisions and known facts

This is a living record from the design grilling. **Settled** items are agreed by the team. **Open** items wait for a research issue. The research items decided during the overnight run of 2026-10-16/17 are under **Overnight decisions (unconfirmed by humans)** until the humans confirm them.

## Settled
- **Name**: `serenedb-log-mcp`.
- **Team**: 3 people. Each person drives their own Claude agents. Time and tokens are not the constraint. The goal is to win, so we do every award track and no half solutions.
- **Stack**: Python with the official MCP SDK, psycopg 3 to SereneDB, `uv` for setup and pytest for tests.
- **Interface**: the MCP server is the product, and Claude (Desktop or Code) is the agent. The Roles are exposed as MCP prompts. There is no custom agent app.
- **Evidence Ledger**: every tool call returns an evidence id, the executed SQL, the parameters, the Data Scope, the total match count, the returned count, a `truncated` flag and the query time. Every call is stored in a ledger. Answers cite `[E<n>]` next to each number. Every answer is split into Observed Facts, Hypotheses, Unknowns and Next Step.
- **Verification**: golden SQL for every worked-investigation claim, enforced by pytest. A replay script re-runs ledger entries and checks the numbers in the final answers.
- **Local dev**: run SereneDB in Docker (`serenedb/serenedb`, port 7890). Point `DATABASE_URL` at either the local instance or the provided instance.
- **Organiser materials**: the official loader, schema and Ownership Table are supplied by the organisers and are the source of truth. We have not received them yet. Until they arrive, a throwaway dev loader unblocks work, and we replace it when the official one lands.
- **Award order**: core requirements first. Best MCP Server is part of the core. Then, in order: agent-managed index with benchmark, huge datasets, multimodal correlation, access control per Role.
- **Multimodal source**: `otel_demo/` in the public-pme bucket, which holds logs, traces and metrics joined on TraceId and stored as remote Parquet. Use Nezha only if we need ground-truth faults.
- **Huge datasets**: query `text_bench/part_000` (1B rows) in place and never index the whole set. The agent builds an index over a time slice on demand. Report rows, wall time and the trade-off between index build time and time saved.
- **Access control per Role**: optional and informal in the brief. SereneDB has no RLS ("Row-level security is not supported"). If we do this track, we use filtered views per Role, a LOGIN role per Role, and GRANT on the views only. The README states the limitation.
- **Log Entries are not incidents**: count entries and derived incidents separately. The incident model was decided overnight (#1) and waits for human confirmation, see "Overnight decisions (unconfirmed by humans)" below.

## Differentiators (settled 2026-10-16)
Most entries will be "an MCP server with search, count and trend tools, plus three answers from Claude". Our edges:
1. **Log Entries are not Incidents, and that is the headline.** Turn line counts into Incidents with Spread or blast radius. BGL node names encode rack, midplane and node card. For example: "152k lines = 3 Incidents: one node looping, one midplane fault, one cluster-wide event". The demo opens with this. Research in #1.
2. **Scored against ground truth.** Report detection results against the BGL alert labels and the OpenStack anomaly instances, such as "found 4/4", in the README and on a slide.
3. **Self-verifying answers.** The agent calls `verify_answer(draft)` before it answers. The tool checks every number and every `[E<n>]` citation against the Evidence Ledger and rejects anything that is unverified or does not match.
4. **The refusal moment.** The Manager asks about cost. The agent refuses to invent a figure, states what the logs measure and what they cannot, and offers the measured alternative.
5. **Visual Evidence inside Claude through MCP Apps** (`io.modelcontextprotocol/ui`, renders in claude.ai and Claude Desktop, not in Claude Code): an incident timeline for the Engineer, a rack heatmap for the Team Lead, a ranked risk table for the Manager. The text `content` fallback is always present. A spike must first confirm that the UI renders over stdio in Claude Desktop. The brief allows a UI ("not required"), and novelty is scored under Execution.
6. **One investigation handed between Roles.** The Engineer, Team Lead and Manager answers chain through shared Evidence ids. We do not give three separate answers.
7. **Baselines on every number**: the previous period, the median week, and a normal or unusual flag.
8. **`export_investigation`** produces the Markdown report of a session. The required worked investigation is generated by this tool, so it can be reproduced.
9. **Demo priority**: line-versus-Incident reveal, then live self-verification, then visuals in Claude, then the ground-truth score, then the refusal. The 1B-row scale result goes on one slide with numbers, not as a live wait.
10. **Optional hosted MCP endpoint** (streamable HTTP, read-only, rate-limited) pointing at the **organiser-provided** SereneDB instance. It is a convenience only. The brief says "use only the tools and resources listed in this brief", so the local stdio path from a clean checkout stays the documented required route.

## Differentiators, round 2 (2026-10-16)
- **Precursor mining (accepted, with a guard).** Across all occurrences of a pattern, find which patterns precede it on the same node within a time window, and compare that rate against the baseline. Report a precursor only when it passes a minimum support and lift threshold that we state. Otherwise answer "no consistent precursor found". No speculative or made-up links.
- **Play to the sponsor (accepted).** Combine search and analytics in one SQL statement (`@@`, BM25, `GROUP BY`, `time_bucket`). Showcase the inverted index over remote Parquet. Show query time in every piece of Evidence. The README gets a "SereneDB features used" section.
- **Pattern-first search (accepted).** The agent searches the template list first and then counts and fetches entries by template id. Vector search is in scope only if it needs no external embedding key.
- **Corpus-relative time (accepted).** Relative times such as "last week" resolve against the corpus end date. The resolved range goes into the Data Scope.
- **Noise versus signal (accepted).** Pareto view in `top_patterns`, with a chronic/benign flag based on level, trend and precursor links.
- **Ownership gaps and cross-team Incidents (parked).** Decide after #4 (Role differentiation) reports.
- **Ticket drafts and decision memo (parked).** Risk of overbuilding. Decide after #4.
- **Hypothesis tracker (dropped).** Out of scope.
- **Judge install (open).** Either a Claude Desktop extension (`.mcpb`) or a self-hosted endpoint. Decide after the spike on MCP Apps over stdio.
- **Demo insurance (accepted).** A recorded backup video and a cached replay of the Evidence.

## Overnight decisions (unconfirmed by humans)
The five former Open research items (template mining, incident model, MCP tool set, eval harness, Role answers) were decided by the overnight Claudes during the run of 2026-10-16/17, together with the embeddings question and the worked investigation. They stay open until the humans confirm them. Each entry links its Decision proposal. The implementation plan is `docs/plan.md`, and the decision log is `docs/overnight-decisions.md`.
- **Incident model** (#1, consensus of both Claudes): an Incident is a maximal chain of Log Entries that share one Pattern, where each entry follows the previous one within `gap_s`. The Pattern is the BGL alert category for alert lines and the template id otherwise. Defaults are `gap_s = 300` (stable band 60–600 s) and `merge_scope = all`, both tool parameters; gaps use a UTC epoch column. Each Incident carries Spread and a Shape label. Derived views: Recurrence (Chronic, New Pattern), Cascade (always a Hypothesis), Episode. OpenStack uses Request Failure, Latency Degradation and Phase-Duration Anomaly. The default Incident table is precomputed at load time; filtered sets are computed at query time. It reproduces Oliner & Stearley's 1,202 BGL failures. https://github.com/OrFrederick/serenedb-log-mcp/issues/1#issuecomment-6226295740
- **Template mining** (#6, decided by the leader alone, follower absent): assign Patterns inside SereneDB in one SQL step after loading, over distinct message texts. Tier 1 is a SQL `CASE` chain generated from the Loghub-2.0 templates with strict wildcards first, scored against the Loghub-2.0 labels as an acceptance gate; Tier 2 is the generic g10 `CREATE MACRO` mask chain for the rest and for OTel (not the label-tuned v10). The output is a Pattern dictionary with one row per distinct message: a content-hash `template_id`, `template_text`, `template_source`, the Loghub-2.0 EventId and a `family_id` that merges the "over N seconds" wording drift. Log Entries join on message text. The plan downloads the Loghub-2.0 files and generates the Tier 1 SQL at derive time without committing either; Tier 1 is on by default (`SLM_PATTERN_TIER1=0` turns it off), and the merge gate is at least 99.99% agreement on covered lines, with 99.9999% as the target. "Pattern" is the concept and `template_id` the column. Drain3 is not needed. https://github.com/OrFrederick/serenedb-log-mcp/issues/6#issuecomment-6226634275
- **MCP tool set** (#2, consensus of both Claudes on OrFrederick's Decision proposal; the round-2 amendments are NoNaim95's alone and not yet confirmed by OrFrederick): read-only, intent-level tools on `mcp` 2.3.0 `MCPServer`: `describe_corpus`, `search_logs`, `get_context`, `count_by` (with a baseline), `trend`, `top_patterns`, `list_incidents`, `latency_stats`, `get_evidence`, `verify_answer`, `export_investigation`, `find_precursors`; stretch `create_index` and `drop_index`. The plan adds `get_role_brief` (#4) and `list_patterns` and `search_patterns` (#7). Every result goes in `structuredContent` as the Evidence envelope; errors are `ToolError`; every tool sets `anthropic/alwaysLoad`; SQL comes from fixed templates with bound parameters in read-only transactions with a client-side `cancel_safe()` timeout. NoNaim95's round-2 amendments: relevance sort is `ORDER BY BM25(...) DESC LIMIT n` with no tie-break key after the score (a two-key BM25 sort crashed native 26.10.1 in 28 of 70 runs); on a lost connection, wait for `select 1`, retry once and add a note, else raise a `ToolError`; `ClientCursor` is optional. https://github.com/OrFrederick/serenedb-log-mcp/issues/2#issuecomment-6225924233 and https://github.com/OrFrederick/serenedb-log-mcp/issues/2#issuecomment-6226499531
- **Eval harness** (#3, decided by the leader alone, follower absent): a thin custom Python harness driving `claude -p` (the judges' client), with deterministic pytest graders in layers: L0 contract (every PR, no LLM), L1 trajectory, L2 grounding, and an optional L3 LLM judge that gates only after calibration. About 40 questions, k = 3 trials, pass^k and Wilson CIs. https://github.com/OrFrederick/serenedb-log-mcp/issues/3#issuecomment-6225712371 (consensus note: https://github.com/OrFrederick/serenedb-log-mcp/issues/3#issuecomment-6226634528)
- **Role answers differ in substance** (#4, consensus of both Claudes): every tool takes a required `role`, which selects the connection, defaults and output shape, and returns an `answer_frame` (plus `not_measured` for the Manager) in `structuredContent`. Guidance through server instructions, MCP prompts and a `get_role_brief` tool. `verify_answer` adds Role checks. Manager ranking is the equal-weight mean of percentile ranks over five Incident-based factors, shown as a top-5 band. Per-Role views and LOGIN roles are defence in depth only. https://github.com/OrFrederick/serenedb-log-mcp/issues/4#issuecomment-6225763701
- **Embeddings** (#7, decided by the leader alone, follower absent): no embeddings in the core path. Claude reads the Pattern catalogue through `list_patterns` and picks Pattern ids, and exact SQL counts by those ids. `search_patterns` (BM25 with stemming over template text plus a committed curated synonym map) is the lexical fallback. Similar Incidents use exact template-set Jaccard plus Component plus Spread, not embeddings. An optional `find_patterns` with `fastembed` vectors (no API key) exists only for the OTel track, as a stretch ticket. https://github.com/OrFrederick/serenedb-log-mcp/issues/7#issuecomment-6226634068
- **Worked investigation** (#5, consensus of both Claudes): "Start-up path failures". Lead: the BGL `/p/gb1` Lustre mount-failure wave (KERNMNTF, 26,426 Log Entries, 83 Incidents). Second Dataset: the 4 labelled OpenStack slow spawns, found by timing. Manager trap: the KERNDTLB single-node storm; the largest KERNDTLB Incident has 152,182 Log Entries on 1 node (2005-06-11), and the category has 152,734 Log Entries. The Manager answer uses two Data Scopes: the wave's window, and the whole BGL Dataset over alert categories with the top-5 band. https://github.com/OrFrederick/serenedb-log-mcp/issues/5#issuecomment-6225730757

## Known facts (verified by research agents, 2026-10-16)
- SereneDB speaks the Postgres wire protocol on port 7890, and psycopg 2 and 3 are supported. Example connection: `psycopg.connect("host=localhost port=7890 dbname=postgres user=postgres")`.
- Full-text search uses an inverted index that you query as its own relation: `FROM idx WHERE col @@ ...`. It supports BM25 (`BM25(idx.tableoid)`), `ts_phrase`, proximity `##`, `ts_levenshtein`, `ts_ngram`, `ts_regexp` and `ts_highlight`. The index is eventually consistent, so run `VACUUM (REFRESH_TABLE) t` after loading. Phrase queries need the `position` dictionary option.
- SereneDB has `time_bucket`, `date_trunc`, `epoch` and `make_timestamp(_ms)`, and full window functions. It has **no** `to_timestamp`.
- Remote Parquet: `read_parquet('https://...')` works. Pass a list of URLs, because HTTPS globs are unlikely to work. `EXPLAIN ANALYZE` reports rows and wall time but not bytes scanned. An inverted index over a view of external data is a snapshot, and you refresh it with `REINDEX`.
- `text_bench`: 52 files of about 1B rows each, about 2 TB in total. `otel_demo/`: logs (91.6M rows), traces (216.7M rows) and metrics.
- Loghub-2.0 (Zenodo 8275861) ships full template annotations: BGL has 4,631,261 lines and 320 templates, OpenStack has 207,632 lines and 48 templates. Its Content field holds only the message, and its line counts differ from the raw corpus.
- OpenStack anomalies: reportedly about 4 instance UUIDs with injected faults, visible in timing data but not in message text. Not yet verified.

## Known facts (verified while fixing the T1 nits, #44, 2026-10-17)
- A **connection** failure on SereneDB 26.09.1.3 carries **no SQLSTATE**: `exc.sqlstate` and `exc.diag.sqlstate` are both `None`, and the class is always `psycopg.OperationalError`. The libpq message is the only thing that tells the causes apart. A statement refused after connecting does carry one (`42501` for `permission denied for schema …`).
- The messages, measured against throwaway containers: nothing listening is `could not receive data from server: Connection refused`; a wrong database is `FATAL: database "x" is not accessible` (**not** PostgreSQL's "does not exist"); an unknown role is `FATAL: role "x" does not exist`; a wrong password is `FATAL: password authentication failed for user "x"`; a role without CONNECT is `FATAL: permission denied for database "x"` with the cause in a second line, `DETAIL: User does not have CONNECT privilege.`
- `CREATE DATABASE`, `CREATE ROLE … LOGIN PASSWORD '…'` and `REVOKE CONNECT ON DATABASE … FROM PUBLIC` all work, and CONNECT is enforced at connect time. A server that asks for a password refuses a password-less role before it checks CONNECT.
- libpq marks `password`, `sslpassword` and `oauth_client_secret` with dispchar `*`, so `pq.Conninfo.get_defaults()` is a reliable source for "which DSN keys are secret"; it also parses a `postgresql://user:password@host` URI into the same keys, which is why one deny-list covers URIs too.
- `docker run -d` whose port bind fails exits 125 and **leaves the named container in `created` state**, so the next run with that name is refused.
- The dev loader streams to COPY: the full BGL corpus (4,747,963 rows) loads with a peak memory footprint of about 33 MiB, down from about 213 MiB when it buffered 200,000 rows.
